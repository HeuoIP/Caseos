# Space Character Dataset

> Knowledge-only artifact. No code. No AI calls.
> This directory is the home of CaseOS "Space Character" understanding:
> what a space IS, what it already HAS, what it LACKS, and what it COULD become.

---

## 1. Purpose

Future CaseOS versions will need to reason about a space BEFORE
recommending objects. That first step is **Space Character**:

- What does the space feel like to be in?
- What physical and contextual strengths does it already have?
- What weaknesses or constraints does it carry?
- What could it become, with the right intervention?

To train and validate that reasoning, CaseOS needs a curated dataset
of reviewed space-character records. This directory is that dataset.

It is the upstream of the Space Character Agent that ADR-006
(Project Fit Architecture) anticipates as a sibling of the Project
Fit Agent.

## 2. Directory Layout

    knowledge/space_character/
        README.md                     # this file
        dataset/                      # approved, structured records (YAML)
        templates/                    # working scratch-pad template (MD)
        examples/                     # placeholder example records (MD)

### 2.1 dataset/

Approved, structured records. One YAML per image. Consumed by the
future Space Character Agent. Schema is a subset of the template
but in YAML so it can be machine-loaded without parsing Markdown.

Empty in Sprint 10.5. First records will be seeded from real
project photos reviewed in the next sprints.

### 2.2 	emplates/

The working scratch-pad used by both AI pre-annotation and human
review. Every record starts as a copy of
space_character_template.md, gets pre-filled by the AI, then
gets reviewed by a human, and only the Final Consensus section
is promoted into dataset/.

### 2.3 examples/

Placeholder example records, one per common site type. They show
the SHAPE of a filled record; they are NOT real projects and
must never be promoted into dataset/.

## 3. Workflow

    1. Pick a real project photo (data/images/cases/0001.jpg, 0002.jpg, ...).
    2. Copy the template:
         cp templates/space_character_template.md \
            working/<image_id>_review.md
    3. AI pre-annotation pass:
         fill the "# AI Analysis" section with a Vision Engine draft.
    "  3a. The Vision Engine is NOT modified for this -- the draft is"
         generated by reading the existing Vision JSON and rendering
         it through a deterministic text template (no LLM call yet).
    4. Human review:
         read the AI section, agree / correct / rewrite.
         record the Agreement Score (1-5) and comments.
    5. Consensus:
         if Agreement Score >= 4, the reviewer fills
         "# Final Consensus" and the record is ready to promote.
         if Agreement Score <= 3, route back to step 3 with a note.
    6. Promote:
         write the four consensus fields to
         dataset/<image_id>.yaml and archive the working MD under
         dataset/_review_history/<image_id>/.

## 4. How Humans Review AI Understanding

The reviewer is a designer / project manager / domain expert.
They are NOT a generic labeler; they need domain experience to
judge whether the AI"s reading of the space is correct.

Review criteria:

1. **Character** -- does the description match what the reviewer
   would feel if they stood in the space?
2. **Strength** -- are the listed strengths physically present, or
   is the AI confabulating?
3. **Weakness** -- are the weaknesses real constraints (climate,
   jurisdiction, fall height), or are they taste complaints?
4. **Potential** -- is the potential achievable in this space, or
   is it wishful thinking?
5. **Atmosphere** -- does the one-sentence atmosphere feel right?

Agreement Score (1-5):

- **5** -- ship as-is.
- **4** -- minor wording, ship.
- **3** -- one substantive section needs rewrite, do not ship.
- **2** -- multiple sections need rewrite.
- **1** -- total rewrite, AI misread the space.

Records with score 4 or 5 may be promoted. Records with score 3
or below are returned for another AI pass with the reviewer"s
corrections included as conditioning input.

## 5. How Reviewed Knowledge Becomes Structured Knowledge

The template MD is the working scratch-pad. The structured dataset
is the SHIPPED artifact. Promotion rules:

1. **Source of truth is the Final Consensus section only.**
   The earlier "AI Analysis" and "Human Review" sections are
   useful for audit, but they are NOT consumed by the agent.
2. **One YAML per record, name = image_id.**
   Path: dataset/<image_id>.yaml.
3. **YAML schema mirrors the consensus fields, plus provenance:**
   `yaml
   image_id: 0001
   site_type: SITE.PUBLIC_PARK
   space_character: "<one paragraph>"
   potential:
     - "<concrete move 1>"
     - "<concrete move 2>"
   priority: MEDIUM
   reviewer: <name>
   reviewed_at: 2026-07-30
   agreement_score: 5
   template_version: v1
   `
4. **No field is invented.** If a section is empty in consensus,
   it stays empty in YAML. The Space Character Agent must learn
   to handle missing fields, not to invent values.
5. **All four consensus fields are required for promotion.**
   Approved Space Character / Approved Potential /
   Approved Priority / Approved Reviewer.

## 6. What This Dataset Is NOT

- NOT a training set for the Vision Engine. The Vision Engine is
  not modified by this dataset; the dataset is consumed by a future
  Space Character Agent that sits AFTER the Vision Engine.
- NOT a replacement for the existing knowledge/objects/ or
  knowledge/taxonomy/theme/ libraries. Those are unchanged.
- NOT a finished product. Sprint 10.5 only builds the structure;
  the first real record will be created in a later sprint.
