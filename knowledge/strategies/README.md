# Strategy Library

The Strategy Library is the **action layer** of CaseOS.

It defines **HOW a Goal is achieved** -- not which equipment to install.

A Goal can be addressed by multiple Strategies.
A Strategy can be implemented by multiple Objects.
An Object can serve multiple Strategies.

This is the Goal -> Strategy -> Object decision chain.

## Why Strategies (not Objects) come first

- Strategies explain **intent** to clients.
- Strategies are reusable across domains (a Landmark can serve a Playground, a Mall, or a Park).
- Strategies make trade-offs visible (e.g., Provide Comfort vs. Interactive Experience).
- Strategies bridge Goals (business intent) with Objects (physical form).

## How Strategies connect to other libraries

- **Strategy -> Goal**: every Strategy lists which Goals it serves (`Addresses_Goals`).
- **Strategy -> Object**: every Strategy lists typical implementations from `knowledge/objects/`.
- **Strategy -> Strategy**: `Synergies` and `Conflicts_With` describe how Strategies interact.
- **Strategy -> Decision**: see `knowledge/reasoning/` for explanation templates.

## Strategy conflict matrix

Some Strategies conflict. The Decision Engine uses `Conflicts_With` to resolve:

- PROVIDE_COMFORT vs. INTERACTIVE_EXPERIENCE (low-stim vs. high-stim)
- PROVIDE_COMFORT vs. CREATE_LANDMARK (subtle vs. attention-grabbing)
- INTERACTIVE_EXPERIENCE vs. CREATE_REST_POINTS (movement vs. stillness)
- IMPROVE_VISIBILITY vs. SUBTLE_INTEGRATION (visible vs. hidden)
- ENABLE_PHOTO_MOMENTS vs. SUBTLE_INTEGRATION (expressive vs. quiet)

## Decision Pipeline

    Client brief
      |
      v
    1. Identify Goals (knowledge/goals/)
      |
      v
    2. Resolve Goal conflicts
      |
      v
    3. Select Strategies (THIS library) per Goal
      |
      v
    4. Resolve Strategy conflicts (Conflicts_With)
      |
      v
    5. Map Strategies -> Object categories (knowledge/objects/)
      |
      v
    6. Generate proposal + reasoning (knowledge/reasoning/)

## Maintenance Rules

1. Strategy_ID is **stable**. Never rename an existing ID; add a new one if needed.
2. The 5-level priority (star count) is the only allowed priority scale.
3. `Addresses_Goals` must reference existing Goal_IDs in `knowledge/goals/`.
4. `Synergies` and `Conflicts_With` must reference existing Strategy_IDs.
5. New Strategies should explain a Mechanism that no existing Strategy already covers.
6. Every change updates `_index.yaml` (regenerated by this renderer).
