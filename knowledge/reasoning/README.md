# Reasoning Library

The Reasoning Library is the **explanation layer** of CaseOS.

It defines **WHY a recommendation is made** -- not the recommendation itself.

In other words: CaseOS doesn't say "we recommend a Treehouse".
CaseOS says:

> Because your goal is "increase enrollment", children aged 3-6 prefer
> role-play and are at a social-language developmental stage that needs
> shared imagination. Your site has existing woodland that amplifies an
> exploration experience. Budget allows the standard scope.
> Therefore: **Treehouse is the highest-ROI option for your goal in your context.**

These explanations are **Decision Reasons**, not Prompts. They are outputs of the AI, not inputs.

## Why Reasoning Library matters

- Clients trust decisions they can understand.
- Reasoning makes AI decisions auditable.
- Reasoning surfaces hidden assumptions.
- Reasoning is what turns CaseOS from a tool into an advisor.

## The 12 Reasoning Patterns

| Reason_ID | Name | Priority | Purpose |
| --- | --- | --- | --- |
| REASON.GOAL_OBJECT_FIT | 目标对象匹配 | ★★★★★ | 对象为什么适合达成目标 |
| REASON.GOAL_STRATEGY_FIT | 目标策略匹配 | ★★★★★ | 策略为什么适合达成目标 |
| REASON.BUDGET_CONSTRAINT | 预算约束 | ★★★★★ | 预算下为什么选这个 |
| REASON.USER_AGE_MATCH | 用户年龄匹配 | ★★★★★ | 为什么匹配该年龄段 |
| REASON.SITE_RESOURCE_MATCH | 场地资源匹配 | ★★★★★ | 为什么用它但不浪费场地优势 |
| REASON.CULTURAL_FIT | 文化匹配 | ★★★★ | 为什么与本地文化上下文一致 |
| REASON.CONFLICT_RESOLUTION | 冲突解决 | ★★★★ | 多个冲突中为什么选这个 |
| REASON.PRIORITY_TRADEOFF | 优先级权衡 | ★★★★ | 为什么顺序是这个 |
| REASON.ROI_CALCULATION | ROI 计算 | ★★★★ | 资本回抩为什么高 |
| REASON.RISK_MITIGATION | 风险缓解 | ★★★★ | 为什么能减少风险 |
| REASON.SUCCESS_PATTERN | 成功模式参考 | ★★★★ | 参考了哪些成功案例 |
| REASON.NEGATIVE_REASON | 排除原因 | ★★★★ | 为什么明确不选某项 |

## Pattern Families

- **JUSTIFY (3)**: GOAL_OBJECT_FIT, GOAL_STRATEGY_FIT, CULTURAL_FIT
- **CONSTRAIN (3)**: BUDGET_CONSTRAINT, USER_AGE_MATCH, SITE_RESOURCE_MATCH
- **RESOLVE (2)**: CONFLICT_RESOLUTION, PRIORITY_TRADEOFF
- **EVALUATE (2)**: ROI_CALCULATION, RISK_MITIGATION
- **CITE (1)**: SUCCESS_PATTERN
- **EXCLUDE (1)**: NEGATIVE_REASON

## How Reasoning is generated

1. The Decision Engine identifies candidate Strategies and Objects.
2. For each candidate, it selects the relevant Reasoning Patterns.
3. It fills the templates with concrete factors (goal, object, benefit, etc.).
4. Patterns are concatenated into a coherent explanation paragraph.

## Template variable syntax

Templates use `{variable}` placeholders. The engine substitutes concrete values:

- `{goal}` -- human-readable goal name (e.g., "increase enrollment")
- `{strategy}` -- strategy name (e.g., "interactive experience")
- `{object}` -- concrete object (e.g., "interactive wall")
- `{benefit}` -- how the object contributes to the goal
- `{site_feature}` -- site-specific resource (e.g., "existing woodland")
- `{age_group}` -- target children age range
- `{budget}` -- budget tier
- `{option}` -- the specific choice being explained
- `{reason}` -- the underlying reason

Reasoning is the bridge between the internal decision chain and the client's understanding.

## Maintenance Rules

1. Reason_ID is **stable**. Never rename an existing ID; add a new one if needed.
2. Each Reason must have at least one Required_Factor and a Template_Chinese.
3. `Uses_Goals` and `Uses_Strategies` reference existing IDs in those libraries.
4. Templates use `{variable}` placeholders, never hardcoded values.
5. Example_Output is mandatory; it anchors the abstract template.
6. Every change updates `_index.yaml` (regenerated by this renderer).
